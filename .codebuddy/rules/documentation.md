# 文档修改规则（Documentation Rules）

## 适用范围
本规则适用于项目中所有文档的编写与修改，包括但不限于：`*.md`、`README`、
`docs/` 目录下的文件、注释文档、接口/使用说明等。

## 规则一：内容补充须有据可依
当现有文档内容或表达不够充分、存在缺口、表述模糊或缺乏说服力时：

1. **优先参考权威来源**补充和丰富内容：
   - 官方技术手册、官方文档、官方规范与 RFC；
   - 主流开源社区中被广泛认可的成熟观点、最佳实践与设计思考。
2. **补充要求**：
   - 内容须准确、可核验，不臆造 API、参数、结论或数据；
   - 引用他人观点或结论时，注明来源（链接 / 出处 / 版本），便于追溯；
   - 区分"官方事实"与"社区建议"，不把社区观点表述为官方结论；
   - 注意技术栈版本一致性，标注信息对应的版本或时间，避免过期内容误导。
3. **表达优化**：在事实准确的前提下，改善结构、逻辑与措辞，使文档清晰、易读、可操作。

## 规则二：提交前必须人工 Review
文档修改完成后，**不得自动提交或 push**，须严格遵循以下流程：

1. 完成修改后，先向用户完整展示改动内容（含变更说明 / diff），
   明确指出补充或调整了哪些部分、依据是什么。
2. **暂停并等待用户 review 与明确确认**，在用户确认无误前不得执行任何提交动作。
3. 仅在用户明确确认（如"确认""可以提交""没问题"）后，才执行：
   - `git add` → `git commit`（提交信息须清晰说明本次文档变更）；
   - `git push` 到原远程仓库分支。
4. 若用户提出修改意见，先按意见调整并再次提交 review，重复本流程直至确认。

## 禁止事项
- 禁止在未经用户确认的情况下提交（commit）或推送（push）任何文档改动。
- 禁止编造无法核验的技术内容、来源或版本信息。
- 禁止将社区观点伪装成官方文档结论。
