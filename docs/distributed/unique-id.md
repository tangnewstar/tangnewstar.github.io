# 分布式唯一id

- 高并发 + 趋势有序：选**Snowflake**（如阿里的 IDWorker、美团的 Leaf-snowflake）。
- 中小规模 + 严格递增：选**Redis 自增**（简单易实现，配合集群保障可用性）。
- 依赖数据库 + 有序性强：选**数据库分段**（如 Leaf 的号段模式，平衡 DB 压力）。
- 快速实现 + 非核心业务：选**UUID**（但避免作为数据库主键）。

### **分布式唯一 ID 生成方案对比**

在分布式系统中，生成全局唯一 ID 是常见需求，需满足：唯一性、有序性、高性能、高可用、可扩展性等特性。以下是几种主流方案的对比：

### **1. 雪花算法（Snowflake）**

**原理**：Twitter 开源的分布式 ID 生成算法，生成 64 位 Long 型 ID，结构如下：

- 1 位符号位（固定 0）
- 41 位时间戳（毫秒级，可使用约 69 年）
- 10 位机器 ID（支持 1024 个节点）
- 12 位序列号（每毫秒最多生成 4096 个 ID）

**优点**：

- 本地生成，无网络开销，性能极高
- 按时间有序，便于排序和分页
- 可自定义 bit 分配，灵活适配场景

**缺点**：

- 强依赖系统时钟，时钟回拨会导致 ID 重复
- 需要提前规划机器 ID，扩容麻烦
- 非纯数字递增（受机器 ID 影响）

**适用场景**：高并发分布式系统（如订单、日志 ID）

### **2. Redis 自增方案**

**原理**：利用 Redis 的`INCR`/`INCRBY`命令实现原子自增，通过设置不同 key 区分业务类型。

**优点**：

- 实现简单，开箱即用
- 天然支持分布式环境
- 纯数字递增，有序性好

**缺点**：

- 依赖 Redis 可用性，单点故障会导致服务不可用
- 高并发下 Redis 可能成为瓶颈
- 无时间戳信息，无法通过 ID 反推生成时间
- 数据持久化配置不当可能导致 ID 重复

**优化方案**：

- 预生成 ID 段（如一次获取 1000 个 ID 到本地），减少 Redis 访问
- 部署 Redis 集群，提高可用性

**适用场景**：中等并发场景，对 ID 有序性要求高

### **3. 数据库分段方案**

**原理**：在数据库中维护 ID 生成表，为不同业务分配 ID 段（如每次取 1000 个），用完后再申请新段。

**实现示例**：

**sql**

```jsx
- ID生成表
CREATE TABLE id_generator ( biz_type VARCHAR(50) PRIMARY KEY, max_id BIGINT NOT NULL, step INT NOT NULL, update_time TIMESTAMP NOT NULL
);
-- 获取ID段（通过SELECT FOR UPDATE保证原子性）
BEGIN;
SELECT max_id, step FROM id_generator WHERE biz_type = 'order' FOR UPDATE;
UPDATE id_generator SET max_id = max_id + step WHERE biz_type = 'order';
COMMIT;
```

**优点**：

- 稳定性高，数据库成熟可靠
- 可通过事务保证原子性
- 易于理解和实现

**缺点**：

- 性能受数据库性能限制
- 单点数据库存在瓶颈风险
- 扩容需修改 step 参数

**优化方案**：

- 分库分表，不同业务使用不同 ID 表
- 本地缓存 ID 段，减少数据库访问

**适用场景**：并发量不高，对稳定性要求高的场景

### **4. 其他方案**

- **UUID/GUID**：
    - 优点：实现简单，无中心化依赖
    - 缺点：无序、字符串存储、占空间大、索引性能差
    - 适用：对 ID 有序性无要求的场景
- **号段模式（Leaf）**：
    - 美团开源方案，结合数据库分段和雪花算法优点
    - 支持号段模式和雪花模式，高可用设计

### **方案对比总结**

| **方案** | **性能** | **有序性** | **可用性** | **实现复杂度** | **适用场景** |
| --- | --- | --- | --- | --- | --- |
| 雪花算法 | 极高 | 时间有序 | 高（本地生成） | 中 | 高并发分布式系统 |
| Redis 自增 | 高 | 严格有序 | 中（需集群） | 低 | 中等并发，有序性要求高 |
| 数据库分段 | 中 | 严格有序 | 高 | 低 | 低并发，稳定性优先 |
| UUID | 高 | 无序 | 极高 | 极低 | 对有序性无要求 |

**选择建议**：

- 高并发核心系统首选雪花算法或其变种（如 Leaf）
- 中小系统可选择 Redis 自增或数据库分段
- 避免在需要排序、分页的场景使用 UUID
- 分布式环境下尽量避免单点依赖（如单一 Redis / 数据库）
