# 分布式共识算法

在分布式系统中，一致性（Consistency）是指多个节点或服务对共享数据的**状态同步能力**，确保不同节点在任意时刻看到的数据是一致的。由于网络分区、节点故障等问题，分布式系统的一致性面临挑战。

### **一致性层级：从强一致到最终一致**

根据数据同步的严格程度，一致性可分为以下层级（CAP理论中的C主要指强一致）：

| **层级** | **定义** | **典型场景** |
| --- | --- | --- |
| **强一致性** | 所有节点在同一时刻看到完全相同的数据（写操作后，所有读操作立即返回最新值） | 分布式数据库（如MySQL主从强一致）、分布式锁 |
| **弱一致性** | 不保证立即同步，允许短暂不一致，但最终会收敛到一致 | 缓存系统（如Redis异步复制） |
| **最终一致性** | 弱一致性的特例，明确保证经过一段时间后所有节点数据一致 | 消息队列（如Kafka）、分布式事务（TCC/Saga） |

### **核心解决方案：按场景分类**

### **1. 共识算法（Consensus Algorithm）：解决“多节点如何达成一致”**

共识算法是分布式一致性的底层基石，用于在不可靠网络中让多个节点对某个值（或操作）达成一致。常见算法包括：

### **（1）Paxos**

- **核心思想**：通过“提案-接受”流程，确保即使部分节点故障，系统仍能选出唯一值。关键角色：提议者（Proposer）、接受者（Acceptor）、学习者（Learner）。流程：Prepare阶段（询问接受者是否接受新提案）→ Accept阶段（正式提交提案）。
- **缺点**：实现复杂，单次提案需多轮交互，性能较低。
- **变种**：Multi-Paxos（优化为“租约+日志复制”，支持顺序写，如Etcd、ZooKeeper的ZAB协议）。

### **（2）Raft**

- **核心思想**：通过“领导者选举+日志复制”简化Paxos，更易理解和实现。关键机制：
    - 领导者选举（Leader Election）：心跳检测，故障时重新选举。
    - 日志复制（Log Replication）：客户端请求由领导者处理，同步到多数节点后提交。
- **优点**：强一致性、高可用（多数派存活即可工作）、易于工程实现。
- **应用**：Etcd、Consul、TiDB（分布式数据库）。

### **（3）Gossip协议（流言协议）**

- **核心思想**：节点间随机传播信息，最终所有节点数据一致（最终一致性）。特点：去中心化、无主节点，适合大规模集群（如Cassandra、Eureka）。
- **缺点**：收敛速度慢（概率性传播），无法保证实时一致性。

### **2. 分布式事务：跨服务/跨库的原子性保证**

当业务涉及多个独立服务或数据库时，需通过分布式事务保证“全成功或全失败”。常见方案：

### **（1）两阶段提交（2PC，Two-Phase Commit）**

- **流程**：① 协调者（Coordinator）发送“准备”请求，所有参与者（Participant）确认可提交；② 若全部确认，协调者发送“提交”指令；否则发送“回滚”。
- **优点**：强一致性（提交前所有节点已锁定资源）。
- **缺点**：
    - 同步阻塞：参与者在等待期间无法处理其他请求；
    - 单点故障：协调者宕机可能导致参与者一直阻塞（需依赖超时机制）；
    - 性能差：多轮网络交互，不适合高并发场景。
- **应用**：传统集中式数据库（如MySQL XA事务）、银行跨行转账。

### **（2）三阶段提交（3PC，Three-Phase Commit）**

- **改进点**：引入“预提交”阶段，增加超时机制，减少阻塞。流程：CanCommit（询问是否可执行）→ PreCommit（执行但不提交）→ DoCommit（正式提交）。
- **缺点**：仍无法彻底解决协调者宕机后的不一致（如网络分区时部分节点提交、部分未提交）。
- **现状**：实际应用较少，仅作为理论优化参考。

### **（3）TCC（Try-Confirm-Cancel，补偿事务）**

- **核心思想**：将业务拆分为三个阶段，通过“预留资源+补偿操作”实现最终一致。流程：
    - Try：预留资源（如冻结账户余额）；
    - Confirm：提交资源（若所有Try成功）；
    - Cancel：释放预留资源（若任一Try失败）。
- **优点**：无长时间资源锁定，适合长事务；支持业务自定义补偿逻辑。
- **缺点**：
    - 业务侵入性强（需实现Try/Confirm/Cancel接口）；
    - 性能开销大（多次交互）；
    - 一致性为最终级别（需处理幂等、防悬挂问题）。
- **应用**：电商大促（库存扣减+订单支付）、金融风控（资金冻结+转账）。

### **（4）Saga模式**

- **核心思想**：将长事务拆分为多个短事务，每个短事务有对应的“正向操作”和“补偿操作”，通过顺序执行或回滚补偿保证最终一致。流程：
    - 正向执行：按顺序执行T1→T2→…→Tn；
    - 回滚补偿：若某一步失败，反向执行补偿Cn→…→C2→C1（需保证补偿的幂等性）。
- **优点**：无中心节点，适合微服务架构；支持异步执行。
- **缺点**：
    - 补偿逻辑复杂（需保证“补偿可重试”“无副作用”）；
    - 最终一致（存在短暂不一致窗口）。
- **应用**：订单履约（下单→扣库存→发货→通知）、物流追踪。

### **3. 最终一致性：异步同步的实践**

对于高并发、低延迟要求的场景，最终一致性通过异步机制实现数据收敛，常见方案：

### **（1）消息队列（MQ）的事务消息**

- **核心思想**：通过“本地事务+消息确认”保证操作与消息的原子性。流程（以RocketMQ为例）：① 发送“半消息”（标记为未提交）；② 执行本地事务（如扣库存）；③ 根据本地事务结果提交或回滚半消息；④ 消费者消费消息并执行下游操作（如创建订单）。
- **关键保障**：
    - 消息可靠性：MQ确保消息不丢失（持久化+重试）；
    - 幂等性：消费者需处理重复消息（如通过唯一ID去重）。
- **应用**：电商下单（库存→订单→支付）、社交动态推送（发帖→通知粉丝）。

### **（2）异步事件驱动（Event Sourcing）**

- **核心思想**：记录所有状态变更事件，通过重放事件重建当前状态。特点：
    - 事件不可变（保证可追溯）；
    - 状态由事件流计算而来（最终一致）。
- **应用**：审计系统（记录所有操作日志）、分布式缓存（缓存更新事件触发同步）。

### **ZAB 与 Raft 的一致性强度：均为强一致，但实现路径不同**

**强一致性**的定义是：所有节点在同一时刻对数据的视图完全一致（写操作后，所有读操作立即返回最新值）。ZAB 和 Raft 均满足这一要求，但实现方式不同：

### **1. ZAB 的强一致性保证**

ZAB 通过 **事务的原子广播（Atomic Broadcast）** 实现强一致：

- Leader 接收客户端事务（如配置变更）后，将其封装为“提案（Proposal）”，并通过两阶段提交（2PC 变种）广播给 Follower：① **准备阶段（PREPARE）**：Leader 向所有 Follower 发送提案（携带 ZXID），Follower 确认接受后回复 ACK；② **提交阶段（COMMIT）**：若多数 Follower 确认，Leader 广播 COMMIT 消息，Follower 提交提案并应用到本地存储。
- 最终所有节点的事务状态完全一致（要么全部提交，要么全部回滚）。

### **2. Raft 的强一致性保证**

Raft 通过 **日志复制（Log Replication）** 实现强一致：

- Leader 接收客户端请求后，将命令封装为日志条目（Log Entry），通过 AppendEntries RPC 同步到多数 Follower；
- 当多数 Follower 确认日志条目已持久化，Leader 将该条目标记为“已提交（Committed）”，并通知 Follower 提交；
- 所有节点按顺序应用已提交的日志条目，最终状态完全一致。
