# MQ → 设计哲学 → 高可用保证

#### RabbitMQ：依赖镜像集群实现分布式高可用

两种种部署模式（单机不讨论）

- 普通集群：集群内多个节点**共享元数据**，但**消息数据只存储在创建队列的实例**
    - **优点**：普通集群可以**提升服务集群吞吐量**
    - 缺点：**本质还是单节点读取。存储队列消息的节点宕机只有等实例恢复才能继续消费**

> 没有做到分布式，消费者拉取数据随机连接节点通过元数据重定向到数据所在节点。或者直连目标节点会导致单实例过热。
> 

- 镜像集群：**集群内多个节点都拥有该队列的完整镜像副本**
    - **优点**：**分布式高可用**，任意节点宕机可连接到其他有数据的节点消费。
    - **缺点**：集群内同步的带宽压力和消耗。不易于扩展，某个队列数据很大时，新增机器要拥有大队列全部数据时，无法线性扩展

*创建队列时，主队列节点**同步元数据到多个实例**。写入消息时主节点**同步消息数据到多个实例**。*

#### Kafka：天然分布式

Kafka集群的分片策略，每个Topic数据会分散到多个Partition，而每个Partition又是多副本的。

因此：**Topic数据是分布在多个机器上**，高可用同时也提供容错

 [MQ → Kafka](../kafka.md) 

#### 比较

Rabbit是传统消息队列，只是提供了集群和HA机制。每个节点都是存储完整队列数据的，只有副本机制容灾而**没有分区机制水平扩展**。

Kafka多个副本中，**Leader副本负责处理Partition读写请求**，**Follower副本异步同步**Leader副本数据单不处理客户端请求。（多副本主从同步）同时实现了容灾与水平扩展的要求
