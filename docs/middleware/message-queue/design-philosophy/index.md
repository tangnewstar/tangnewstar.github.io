# MQ → 设计哲学

<aside>
💡

消息队列的优点：**解耦，异步，削峰**

</aside>

- **解耦**：上游产生的业务数据下游多个系统接收

传统：通过 RPC（HTTP）**服务调用**由上游直接通知下游

问题：数据结构变化，下游系统增减，需要**修改上游代码或配置**。还要引入重试机制（确保数据有效传递）

解决：生产端（上游）不需要关心消费，需要数据的消费者可按需求订阅。失败重试也只需要消费端负责。

- **异步**：系统产生的业务数据需要写入多库表

<aside>
💡

订单服务：写入订单表 → 记录订单明细 → 记录订单优惠信息 → 积分累计

然后不同队列的消费者异步去进行数据库的写入操作。

解决：将3条消息发送到对应队列，立即返回前端订单结果。感知延时低。

如果后面几步是耗时操作（超过200ms）将影响核心链路延时。

</aside>

- **削峰**：系统存在明显短暂的业务高峰。

场景：业务高峰（10点到11点）请求量激增过后又恢复正常。

问题：后端某些组件天然**单节点**且存在 QPS 上限（例如 MySQL 每秒写入 2000）

解决：为保障系统稳定可用，需要对高峰期产生的大量请求进行削峰

> MQ作为数据缓冲，不直接写库。按照数据库的负载能力按一定速率（例如每秒2000条）从MQ拉取消息再落库。**平衡了系统吞吐量与单点稳定可用**。缺点：数据写入延迟，高峰过后逐步追上。
>

### 保证消息的顺序消费

- **RabbitMQ（拆分队列保证每个队列内的顺序 or 队列Consumer内创建多个内存队列来排队处理保证每个内存队列的有序）**
    
    拆分多个 queue，每个 queue 一个 consumer，就是多一些 queue 而已，确实是麻烦点，这样也会造成吞吐量下降，可以在消费者内部采用多线程的方式取消费。
    
    ![rabbitmq-order-02](https://java.doocs.org/assets/rabbitmq-order-02.hXsmplBa.png)
    
    或者就一个 queue 但是对应一个 consumer，然后这个 consumer 内部用内存队列做排队，然后分发给底层不同的 worker 来处理。
    
    注意，这里消费者不直接消费消息，而是将消息根据关键值（比如：订单 id）进行哈希，哈希值相同的消息保存到相同的内存队列里。也就是说，需要保证顺序的消息存到了相同的内存队列，然后由一个唯一的 worker 去处理。
    
- **Kafka（partition消费者创建多个内存队列相同key的数据到同一个内存queue保证有序性）**
    - 一个 topic，一个 partition，一个 consumer，内部单线程消费，单线程吞吐量太低，一般不会用这个。
    - 写 N 个内存 queue，具有相同 key 的数据都到同一个内存 queue；然后对于 N 个线程，每个线程分别消费一个内存 queue 即可，这样就能保证顺序性。
