# MQ场景 - 消息积压

#### 核心业务恢复

- 扩容实例（水平扩展）
    - 消费者扩容：增加消费者线程（线程池）消费者实例
    - MQ扩容：Kafka Partition扩容（应对消费者数量已满）RocketMQ增加实例
- 降级限流：对于前端无意义重试可以在网关层限流，非必要关闭生产
- 异常隔离：将反复报错的**异常消息临时跳过或转入死信队列**，不阻塞其他正常消息
- 异步处理：消费逻辑慢，可以**先落库再异步任务**去处理

#### 排查原因

消息积压本质：生产者速度 > 消费者速度

沿着消息生产链路：生产者 → MQ → 消费者 逐步排查

- **生产者：服务TPS是否上升**（平稳上升还是突然增加）
    - 排查思路：哪个服务产生的，是否有代码逻辑错误（定时任务，死循环）
    - 可能原因：
        - **业务流量增加**：运营活动，大促，功能上线带来的自然流量
        
        也可能是批量导数，定时任务，或者上游业务bug
        
        - **消息重试**：网络抖动或Broker响应延迟（失败自动重试）重试机制不合理
        - **消息格式异常**：消息体积增加Broker处理变慢，消费端解析耗时增加。或字段不兼容解析失败。
- Broker：**单个队列积压还是全量队列积压**
    - 排查思路：检查硬件资源CPU，内存，磁盘使用率，网络IO，确认网络是否有延迟
    - 可能原因：
        - **机器资源瓶颈**：CPU/内存打满负载过高，磁盘IO瓶颈（同步刷盘），网络带宽不足
        - **分区/负载不均**：
            - 消息分区不均：partition key不合理，大量消息被哈希到同一分区
            - 节点分配不均：队列在Broker节点上分配不均，少数节点承受多数流量
        - **中间件故障与配置**
            - 节点宕机/重启/Leader切换，故障期间形成积压
            - 副本同步异常：主从同步延时，ISR列表收缩
            - 系统流控：Broker触发内存/磁盘/连接数流控，主动降低生产消费速率
- 消费者：**消费者TPS是否大幅下降**
    - 排查思路：
        - 节点状态：进程假死（线程池满/OOM）频繁Full GC，频繁重启
        - 服务日志：大量报错（空指针，反序列化失败，死锁）无限重试一条错误消息
        - 下游依赖：数据库是否存在慢SQL，是否死锁连接池耗尽；下游RPC是否超时。
    - 可能原因：
        - **单条处理耗时明显增加**：下游依赖变慢（数据库/RPC）业务逻辑变更（上线耗时操作）锁竞争（分布式锁，本地锁）
        - **线程池阻塞/耗尽**：线程池占满，逻辑死循环，频繁Ful GC（内存泄漏）
        - **消费失败重试**：消费逻辑异常反复重试，消息格式异常全部进入重试链路
        - **消费能力不足/负载不均**：消费者实例不够，并发配置过低（线程池/拉取数），分区分配不均（消费者负责的分区数不同出现短板实例）

监控 → 变更 → 日志 → 资源 → 定位耗时操作
