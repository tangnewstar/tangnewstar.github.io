# TCP协议的粘包拆包

TCP 协议本身是**流式协议**，它不保留消息边界，这意味着发送方发送的数据可能会被接收方拆分成多个数据包（拆包），或者多个发送的数据包会被接收方合并成一个数据包（粘包）。这种现象称为**TCP 粘包和拆包**，是网络通信中常见的问题。

### **1. TCP 是流式协议**

- 数据在传输时被视为**连续的字节流**，而不是分帧的。
- 报文头（Header）只有 IP 地址和端口等基础信息，没有消息长度或消息边界标识。

### **2. 粘包（Sticking）**

- 当发送多个小数据包时，接收方可能会把它们合并为一个数据包。
- 示例：发送 "Hello World" 和 "How are you"，接收方可能一次性接收到 "Hello WorldHow are you"。

### **3. 拆包（Splitting）**

- 大数据包可能会被拆分成多个小数据包传输。
- 示例：一次发送一个 10KB 的文件，可能会拆分成多个 2KB 的 TCP 数据包。

### **4. 粘包和拆包的后果**

- 造成接收端无法正确解析数据边界，影响业务逻辑（如消息丢失或重复）。

常见情况：

**拆包**

- 报文内容大小TCP层MSS限制（1460 byte，在MTU（1500byte）基础上减去20的IP头和20的TCP头）。当超过限制后，TCP会强制拆分多个报文，确保每个小于MSS。

**粘包**

- **Nagle算法缓存累积：发送方未确认（ACK）的小数据包会缓存起来，等待接收方ACK后再立即发送缓存的数据包或是等待缓存的数据超过MSS。**
- **接收方缓冲区合并读取**：如果接收方缓冲区到达多个消息，recv会一次性读取所有数据。

### **二、发送时机的决定：TCP如何决定何时发送数据？**

发送方调用`send()`将数据写入发送缓冲区后，TCP需要决定何时将缓冲区中的数据发送出去。核心决策因素包括：

### **1. Nagle算法的缓存策略**

- **规则**：若发送方有**未确认的小数据包**（≤MSS且未被ACK确认），新写入的小数据会被缓存，直到：
    - 之前的数据被ACK确认（此时缓存数据会被立即发送）；
    - 或缓存数据达到MSS大小（此时合并发送）。
- **示例**：
    - 发送方发送100字节（小数据），未收到ACK时，又写入200字节（新数据）；
    - Nagle算法将300字节缓存（若MSS≥300），待第一个100字节的ACK到达后，立即发送300字节的报文段。

### **2. MSS限制**

TCP报文段的数据部分（负载）不能超过MSS（由三次握手协商确定）。若发送缓冲区中的数据超过MSS，TCP会强制拆分为多个报文段（每个≤MSS）发送。

### **3. 拥塞窗口（cwnd）**

拥塞窗口是TCP根据网络拥塞状态动态调整的“允许发送的最大数据量”。发送方每次最多只能发送`min(接收窗口, 拥塞窗口)`大小的数据。

### **4. 接收窗口（rwnd）**

接收窗口由接收方通过TCP报文中的“窗口大小”字段通知发送方，表示接收方当前可用的接收缓冲区容量。发送方发送的数据量不能超过接收窗口，否则会导致接收方缓冲区溢出。

### **5. 延迟确认（Delayed ACK）的影响**

接收方可能延迟发送ACK（通常延迟200ms），以等待是否有后续数据到达（合并ACK）。这会导致发送方的Nagle算法缓存时间延长，进一步推迟数据发送。

### **三、接收时机的决定：TCP如何决定何时接收数据？**

接收方的接收时机主要由**应用层的读取操作**和**TCP的滑动窗口机制**共同决定。

### **1. 应用层主动读取（核心触发）**

接收方的TCP接收缓冲区存储了TCP报文段的数据，但应用层必须调用`recv()`/`read()`主动读取数据。TCP本身不会主动将数据“推送”给应用层（除非应用层设置了“紧急模式”或使用了带外数据）。

### **2. TCP滑动窗口的控制**

- **接收窗口（rwnd）**：接收方通过TCP报文告知发送方自己的接收缓冲区剩余容量。若接收缓冲区已满（rwnd=0），发送方会暂停发送数据，直到接收方通知窗口更新（Window Update）。
- **零窗口探测（Zero Window Probe）**：若接收方窗口为0，发送方会定期发送1字节的探测报文，询问接收方窗口是否恢复，避免死锁。

### **3. 数据的重组与排序**

TCP接收缓冲区会按序列号对收到的报文段进行排序和重组。若报文段乱序到达，TCP会暂存乱序数据，直到缺失的报文段到达后才交付给应用层。

### **一、粘包（多个应用层消息合并为一个/多个TCP报文段）的常见场景**

粘包的核心是“多个应用层消息被TCP合并传输”，常见于以下场景：

### **1. Nagle算法缓存累积（最典型）**

TCP的Nagle算法默认开启，目标是减少小数据包数量。规则：若发送方有**未确认的小数据包**（未收到ACK），新数据会被缓存，直到：

- 之前的数据被确认（ACK到达）；
- 或缓存数据达到MSS大小（此时合并发送）。

**示例**：

发送方连续调用两次`send`，分别发送100字节的消息A和200字节的消息B：

- 第一次发送的100字节（小数据）因未确认被缓存；
- 第二次发送的200字节会被合并到缓存中（总300字节），若MSS≥300字节，则合并为一个TCP报文段发送；
- 接收方一次`recv`读取300字节（A+B），感知为粘包。

### **2. 接收方缓冲区合并读取**

接收方的TCP接收缓冲区会暂存所有收到的TCP报文段数据。当应用层调用`recv`时：

- 若缓冲区中有多个应用层消息的缓存数据（如消息A和B已全部到达），`recv`会一次性读取所有可用数据（A+B）；
- 若应用层未及时读取（缓冲区堆积），后续到达的消息会继续累积，进一步加剧粘包。

**示例**：

发送方依次发送消息A（100字节）、B（200字节）、C（300字节）；

接收方因处理延迟，第一次`recv`读取了600字节（A+B+C），直接合并为一个大字节流，需应用层自行拆分。

### **3. 应用层高频发送小数据**

若应用层短时间内连续发送多个小数据（如心跳包、短指令），且每个数据量小于MSS：

- 即使Nagle算法未触发（如无未确认数据），TCP可能因发送缓冲区未填满，将这些小数据暂存，等待后续数据到来后合并发送；
- 接收方可能一次性读取多个小数据的合并结果，形成粘包。

### **二、拆包（单个应用层消息拆分为多个TCP报文段）的常见场景**

拆包的核心是“单个应用层消息被TCP拆分为多个报文段传输”，常见于以下场景：

### **1. MSS（最大段大小）限制（最主要原因）**

TCP报文段的有效载荷（数据部分）最大为MSS（通常≈MTU-IP头-TCP头≈1460字节）。若应用层消息长度超过MSS，TCP会强制拆分为多个报文段（每个≤MSS）。

**示例**：

发送方发送一个2000字节的消息，MSS=1460字节：

- TCP拆分为1460字节（报文段1）和540字节（报文段2）两个TCP报文段；
- 接收方需调用两次`recv`（第一次读1460字节，第二次读540字节），才能拼接完整消息。

### **2. IP层分片（MTU限制）**

IP层对数据报的最大长度（MTU，通常1500字节）有限制。若TCP报文（含IP头+TCP头+数据）超过MTU，IP层会将其分片传输：

- 每个IP分片独立传输，接收方需重组分片后才能交付给TCP层；
- 若其中一个分片丢失，整个IP数据报需重传，可能导致应用层收到不完整的“拆包”。

**示例**：

发送方发送一个1600字节的TCP报文（IP头20字节+TCP头20字节+数据1560字节），MTU=1500字节：

- IP层拆分为：第一个分片（1500字节，含IP头+TCP头+数据1460字节），第二个分片（160字节，仅数据）；
- 接收方需重组两个分片后，TCP层才能提取完整数据。
