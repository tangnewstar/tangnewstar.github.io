# JVM内存分布

### **1. JVM 内存区域划分**

- **堆（Heap）**
    - 所有线程共享的内存区域，用于存储对象实例和数组
    - 是垃圾回收的主要区域，按对象生命周期分为新生代（Eden 区、Survivor 区）和老年代
    - 大小可通过`Xms`（初始堆大小）和`Xmx`（最大堆大小）参数调整
- **方法区（Method Area）**
    - 线程共享区域，存储类信息、常量、静态变量、即时编译器编译后的代码等
    - JDK8 及以后以元空间（Metaspace）实现，不再使用永久代，元空间使用本地内存
    - 当方法区无法满足内存分配需求时，会抛出 OutOfMemoryError
- **虚拟机栈（VM Stack）**
    - 线程私有，每个方法执行时会创建一个栈帧（存储局部变量表、操作数栈、动态链接、方法出口等）
    - 生命周期与线程相同，方法调用对应栈帧入栈，方法返回对应栈帧出栈
    - 栈深度超过虚拟机允许的范围会抛出 StackOverflowError
- **本地方法栈（Native Method Stack）**
    - 与虚拟机栈功能类似，主要为 Native 方法（非 Java 语言实现的方法）服务
    - 具体实现依赖于虚拟机，HotSpot 虚拟机将其与虚拟机栈合二为一
- **程序计数器（Program Counter Register）**
    - 线程私有，记录当前线程执行的字节码指令地址
    - 如果执行的是 Native 方法，计数器值为 Undefined
    - 是 JVM 中唯一不会抛出 OutOfMemoryError 的区域

### **2. 垃圾回收机制（Garbage Collection, GC）**

垃圾回收是 JVM 自动管理内存的核心机制，主要负责回收堆中不再被使用的对象内存。

#### **垃圾判断算法**

- **引用计数法**：为每个对象设置引用计数器，有引用时加 1，引用失效时减 1，计数器为 0 的对象可回收（缺点：无法解决循环引用问题）
- **可达性分析**：以 GC Roots 为起点，通过引用链遍历对象，不可达的对象被标记为可回收（主流 JVM 采用的算法）
    - GC Roots 包括：虚拟机栈中引用的对象、方法区中类静态属性引用的对象、方法区中常量引用的对象、本地方法栈中 JNI 引用的对象等

#### **垃圾回收算法**

- **标记 - 清除算法**：先标记可回收对象，再统一清除（缺点：产生内存碎片）
- **复制算法**：将内存分为两块，只使用其中一块，回收时将存活对象复制到另一块（优点：无内存碎片；缺点：内存利用率低）
- **标记 - 整理算法**：标记后将存活对象向一端移动，然后清理边界外的内存（适用于老年代）
- **分代收集算法**：根据对象存活周期将内存分代，不同代采用不同回收算法
    - 新生代：对象存活率低，采用复制算法
    - 老年代：对象存活率高，采用标记 - 清除或标记 - 整理算法

### **常见垃圾收集器**

- Serial GC：单线程收集，收集时暂停所有用户线程（简单高效，适用于单核环境）
- Parallel GC：多线程收集，注重吞吐量（吞吐量 = 运行用户代码时间 /(运行用户代码时间 + GC 时间)）
- CMS（Concurrent Mark Sweep）：并发收集，尽可能减少停顿时间（注重响应速度）
- G1（Garbage-First）：将堆划分为多个区域，按区域优先级进行回收（兼顾吞吐量和响应速度）

JVM 的内存模型和垃圾回收机制共同保证了 Java 程序的内存安全和高效运行，自动内存管理机制大大减少了内存泄漏和野指针等问题。

是否遇到过线上OOM问题？如何排查和解决的？

| **OOM 类型** | **错误信息关键词** | **常见原因** |
| --- | --- | --- |
| 堆内存溢出（最常见） | `java.lang.OutOfMemoryError: Java heap space` | 对象创建过多且未被 GC 回收（内存泄漏或大对象） |
| 方法区 / 元空间溢出 | `java.lang.OutOfMemoryError: Metaspace` | 类加载过多（如动态生成类、依赖冲突导致类重复加载） |
| 直接内存溢出 | `java.lang.OutOfMemoryError: Direct buffer memory` | NIO 直接内存使用超限（未及时释放） |
| 栈内存溢出 | `java.lang.StackOverflowError` | 递归调用过深或线程栈设置过小 |
