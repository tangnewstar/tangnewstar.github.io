# G1

🧠 **理解GC的几个关键点**

- **吞吐量（Throughput）**：应用程序运行时间占总时间（应用程序运行时间 + GC时间）的比值。
- **延迟（Latency）**：GC发生时，导致的应用程序**停顿时间（STW）**。这是我们通常最敏感的指标。
- **内存开销（Footprint）**：GC算法本身需要的数据结构和空间开销。

### **📜 从Serial到ZGC的演进之旅**

GC算法最初的形态是**标记-清除（Mark-Sweep）**7。这是一种非常直接的思路：先标记所有存活对象，然后清除未标记的垃圾。但它有两个明显缺点：**内存碎片**和**分配延迟**7。

为了克服标记-清除的碎片问题，**标记-复制（Mark-Copy）**算法被提出7。它将内存一分为二，每次只使用一半，GC时将存活对象复制到另一半，然后清空当前半区。优点是**无碎片，分配快**，但代价是**内存利用率最高仅50%**7。

IBM的研究对标记-复制算法进行了优化，他们发现**按8:1比例划分Eden区和Survivor区，内存利用率可达90%**7。

另一种解决碎片的方法是**标记-整理（Mark-Compact）**7。它在标记后会将所有存活对象向一端移动，然后清理边界外的内存。它**兼具标记-清理的内存利用率和标记-整理的连续空间优势**，但**对象移动带来的二次遍历开销**是其性能瓶颈7。

基于**弱分代假说**（绝大多数对象"朝生暮死"）和**强分代假说**（经历多次GC的对象更难消亡），**分代回收（Generational GC）**革命性地引入了**时间维度**7。它将堆内存划分为**新生代**（Young Generation）和**老年代**（Old Generation），针对不同代际对象的特点采用不同的GC策略7。

为了实现分代思想，GC算法引入了**写屏障（Write Barrier）**和**卡表（Card Table）**（以512字节为粒度记录老年代对新生代的引用）等关键技术

### **第一阶段：Serial GC - 奠基者**

- **出现背景**：Java的初衷是“一次编写，到处运行”，需要**自动化**的内存管理来避免手动管理的陷阱。早期的计算机大多是单核的。
- **解决的核心问题**：提供了**自动化**的内存管理，将程序员从复杂且易错的手动内存管理中解放出来。
- **工作原理**：
    - **新生代**：采用 **“Stop-Copy”** 算法（Serial Copying），在回收时暂停所有应用线程（Stop-The-World, STW），然后将存活对象复制到另一个幸存区。
    - **老年代**：采用 **“标记-整理”** 算法（Mark-Sweep-Compact），同样是STW，先标记存活对象，然后进行清理和压缩以避免碎片。
- **自身缺点**：
    - **STW时间过长**：无论是年轻代还是老年代GC，都会导致整个应用“卡死”，对于交互式应用体验极差。
    - **单线程效率瓶颈**：无法利用多核CPU的优势。

### **第二阶段：Parallel (Throughput) GC - 效率追求者**

- **出现背景**：多核服务器开始普及。出现了需要大量后台计算、对任务完成时间（吞吐量）有要求，但对单次停顿不敏感的场景（如批处理作业）。
- **解决的核心问题**：解决Serial GC**吞吐量低**的问题，充分利用多核CPU资源来**加快GC速度**，减少GC的总耗时。
- **工作原理**：它是Serial GC的**多线程版本**。
    - **新生代**：**Parallel Scavenge**，多线程并行地执行复制操作。
    - **老年代**：**Parallel Old**，多线程并行地执行标记-整理。
- **自身缺点**：
    - **更激烈的停顿**：虽然总的GC时间变短了（吞吐量高），但STW期间所有CPU核心都在全力做GC，这会导致**停顿期间的应用程序性能“毛刺”更加明显**。它用更强的STW换取了更短的STW时间。

### **第三阶段：CMS (Concurrent Mark-Sweep) GC - 延迟挑战者**

- **出现背景**：Java广泛应用于Web服务、B/S系统等对**响应时间**极其敏感的场景。人们无法接受一次GC就服务中断数百毫秒甚至数秒。
- **解决的核心问题**：**最大限度地减少GC停顿时间**，让GC线程尽可能多地与用户线程**并发**执行，从而提升应用程序的响应速度。
- **工作原理**：过程复杂，分为多个阶段，其中初始标记和重新标记是STW的，而**并发标记**和**并发清理**是与用户线程一起执行的。
- **自身缺点**（非常典型，正是这些缺点催生了G1）：
    1. **对CPU资源敏感**：并发阶段GC线程会抢占用户线程的CPU资源，导致应用吞吐量降低。
    2. **“浮动垃圾”**：并发清理阶段用户线程还在运行，会产生新的垃圾，只能留到下一次GC再清理。
    3. **最致命的问题：内存碎片**。由于使用**标记-清除**算法，不会压缩内存。运行一段时间后，老年代会充满碎片。当无法找到足够大的连续空间分配大对象时，会触发一次悲壮的 **“Serial Old GC”** （单线程Full GC），进行一次彻底的压缩整理，这个过程会产生**极长的STW停顿**，违背了CMS设计的初衷。
    4. **复杂度高**，调参困难。

### **第四阶段：G1 (Garbage-First) GC - 平衡与革新者**

- **出现背景**：堆内存越来越大（几十GB），CMS的碎片化问题几乎无解。需要一款能**应对大内存**、同时提供**相对可控的停顿时间**的收集器。
- **解决的核心问题**：
    1. **解决CMS的内存碎片问题**。
    2. **提供可预测的停顿模型**（软实时），用户可以指定期望的停顿时间目标。
- **工作原理的革命性**：
    - **内存布局革新**：不再坚持物理上的连续分代，而是将堆划分为多个大小固定的 **Region**。Region可以扮演Eden、Survivor、Old、Humongous（存放大对象）等角色。
    - **回收思路革新**：G1跟踪各个Region的“垃圾价值”（回收能获得的空间大小以及所需时间），每次回收时，优先回收价值最大的那些Region（Garbage-First名的由来）。这保证了在有限的时间内（用户设定的停顿时间）做收益最高的事。
    - **算法**：整体上看是“标记-整理”，在两个Region之间是“复制”。这**从根本上避免了内存碎片**。
- **自身缺点**：
    - **内存开销**：G1自身的数据结构（如Remembered Sets）会占用更多的内存（通常约10%-20%）。
    - **并非全并发**：其初始标记和最终标记阶段仍然需要短暂的STW。
    - **小内存应用可能不如Parallel GC**：对于小堆，G1的管理开销可能显得不划算。

### **第五阶段：ZGC / Shenandoah - 未来的超低延迟先锋**

- **出现背景**：内存价格下降，数百GB甚至TB级别的堆内存成为现实。在金融交易、实时大数据平台等场景下，**任何超过10毫秒的停顿都是不可接受的**。G1的停顿时间（几十到百毫秒）无法满足要求。
- **解决的核心问题**：**将GC停顿时间缩短到10ms以下，甚至亚毫秒级，并且停顿时间不会随着堆容量的增大而增长**。
- **工作原理的革命性**（以ZGC为例）：
    - **染色指针**：将**元数据**（如标记信息、重定位信息）存储在指针本身中，而不是对象头里。这是实现并发整理的基石。
    - **读屏障**：在应用程序线程从堆中加载引用时，插入一小段代码（读屏障），用于检查“染色指针”的状态。这个屏障可以**在用户线程执行过程中，异步地处理对象的重定位和引用的修正**。
    - **全并发**：得益于上述技术，ZGC的**标记、转移（移动对象）、重映射（修正指针）** 阶段几乎都是并发执行的。其STW阶段只存在于GC Roots扫描，耗时极短且与堆大小无关。
- **自身缺点**：
    - **更高的内存开销**：为了实现并发转移，需要额外的空间。
    - **吞吐量可能略有下降**：读屏障会对每次指针访问增加一点开销，虽然极小，但会略微降低应用的吞吐量。

### **总结**

GC的进化之路，是一个不断解决前代缺陷、适应新硬件和新应用场景的过程：

- **Serial -> Parallel**：解决了**吞吐量**问题，代价是更激烈的STW。
- **Parallel -> CMS**：解决了**延迟**问题，但带来了**碎片化**和**复杂度**。
- **CMS -> G1**：解决了**碎片化**问题，并提供了**可预测的停顿**，为**大堆**设计。
- **G1 -> ZGC/Shenandoah**：目标是**近乎无停顿**，解决**超大堆下的延迟**问题，代价是**更复杂的设计和略微的吞吐量损失**。

为什么G1适合大堆？

**解决的核心问题**：传统的CMS回收器在回收老年代时，必须扫描整个老年代空间。当堆很大时，这个过程非常缓慢，导致长时间的STW停顿。CMS使用的“标记-清除”算法会产生内存碎片，在大堆环境下，碎片积累到一定程度后触发Full GC（Serial Old）的停顿时间会长得无法接受。

**G1的优势**：G1不再以整个代为单位进行回收。它每次回收只关注**一部分Region**（称为**Collection Set**）。这意味着无论堆总共有多大，**单次回收的工作量只由本次选择的Region数量决定**，从而将庞大的回收任务切割成了多个小块。

为什么ZGC适合超大堆？

**解决的核心问题**：无论是G1还是之前的收集器，其“标记-整理”过程中的**对象移动**环节都必须是STW的，因为移动对象的同时要修正所有指向它的引用，这个操作非常复杂。堆越大，存活对象越多，这个STW时间就越长。

**ZGC的优势**：ZGC连“对象移动”这个最重的操作都做到了并发！这意味着应用程序仅在GC开始时有一个极其短暂的STW（用于Root扫描，通常<1ms），之后所有的耗时工作都在后台并发完成了。

Q1: 什么时候触发youngGC？

年轻代空间不足够分配时

Q2：JVM G1收集器堆内存分配2G，年轻代的大小最大能分配多少？

在JVM中，当使用G1（Garbage-First）收集器且堆内存分配为2G时，**年轻代的最大大小由参数G1MaxNewSizePercent控制**，其默认值为堆内存的60%

**默认最大值**

- **核心参数**：**G1MaxNewSizePercent**（默认60%）决定了年轻代占用堆内存的最大比例。
- **计算公式**：**年轻代最大大小 = 堆总大小 × G1MaxNewSizePercent** 当堆内存为2G时，默认年轻代最大值为：**2G × 60% = 1.2G**（即1228.8MB）

**动态调整**

G1收集器会根据目标停顿时间（**MaxGCPauseMillis**，默认200ms）动态调整年轻代实际大小，而非始终使用最大值

- **触发条件**：若Young GC时间远小于**MaxGCPauseMillis**，G1会增大年轻代Region数量以提升吞吐量；反之则会减少以缩短GC停顿[⁠⁣](https://juejin.cn/post/7066242120733949960)
- **实际值范围**：年轻代实际大小通常介于**G1NewSizePercent**（默认5%）到**G1MaxNewSizePercent**（默认60%）之间
