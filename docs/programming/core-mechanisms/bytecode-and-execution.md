# 字节码与执行引擎

Java 源码要先编译成 `.class` 文件，JVM 在运行时加载它，再由执行引擎执行其中的字节码。本篇按“怎么编出来 → 文件里是什么 → 怎么读 → 怎么执行”的顺序展开，重点是最后的执行引擎。

## 从 .java 到 .class

先说编译过程。`javac`（或 IDE、构建工具）把 `.java` 源文件变成 `.class`：

```text
.java 源文件
  → 词法分析：拆成关键字、标识符、字面量等 token
  → 语法分析：按语法规则组成抽象语法树（AST）
  → 语义分析：类型检查、符号表解析、注解处理
  → 生成字节码：把 AST 翻译成 JVM 指令，并生成常量池、字段表、方法表
  → .class 文件
```

对应到命令就是：

```bash
javac Demo.java   # 编译期：生成 Demo.class
java Demo         # 运行期：JVM 加载 Demo.class 并执行
```

几个关键点：

- 这是**编译期**发生的事，发生在 JVM 启动之前；`.class` 是编译后的产物，不是运行时临时生成的（动态生成类的场景除外，如 ASM、Lambda）。
- 一个 `.java` 文件可能编译出**多个** `.class`（内部类、匿名类、Lambda 等都会生成独立 class）。
- 运行时 JVM 通过类加载器读取 `.class` 字节流，把类元信息放进方法区、生成 `Class` 对象，执行引擎再执行其中的字节码。这部分见 [类加载机制](class-loading.md)。

## .class 文件里有什么

`.class` 是**编译后的二进制文件格式**，运行时 JVM 按这个格式把文件解析成内存中的数据结构。它是一组以 8 字节为单位的二进制流，主要包含：

- **magic（`0xCAFEBABE`）** 与版本号：标识这是一个 class 文件，以及目标 JVM 版本；
- **常量池**：字面量、类/字段/方法的符号引用，是 class 文件中占比最大的部分；
- **访问标志、类索引、父类索引、接口索引**：描述类的继承关系与访问属性；
- **字段表、方法表**：每个方法的 `Code` 属性存放字节码指令、操作数栈深度与局部变量表，这是执行引擎真正读取的内容；
- **附加属性**：`LineNumberTable`、`LocalVariableTable`、`Exceptions`、`SourceFile` 等调试与元信息。

<aside>
💡

简单区分：**编译期**产出 `.class` 这种静态文件；**运行时** JVM 加载它，按上述结构解析为方法区中的元数据与字节码指令，再由执行引擎执行。

</aside>

## 示例：用 javap 读字节码

`javap` 是 JDK 自带的反汇编工具，读取的是**编译后的 `.class` 文件**。

```bash
javac Demo.java
javap -c -p -v -l com.example.Demo
# -c 反汇编字节码  -p 显示私有成员  -v 输出常量池/属性等详细信息  -l 显示行号表
```

假设源码里有一个方法：

```java
public int add(int a, int b) {
    return a + b;
}
```

`javap -c` 输出（局部变量槽 0 是 `this`）：

```text
public int add(int, int);
  Code:
     0: iload_1     // 把局部变量 1（a）压入操作数栈
     1: iload_2     // 把局部变量 2（b）压入操作数栈
     2: iadd        // 弹出两个 int，相加后结果入栈
     3: ireturn     // 返回 int
```

从这里能直观看到：源码中的 `a + b` 被拆成了“加载 → 运算 → 返回”几条字节码指令，执行引擎就是逐条处理这些指令的。

常见指令分类：

- 加载/存储：`iload`、`istore`、`aload_0`、`astore`；
- 运算与类型转换：`iadd`、`imul`、`i2l`；
- 对象与数组：`new`、`newarray`、`getfield`、`putstatic`；
- 方法调用：`invokevirtual`、`invokespecial`、`invokestatic`、`invokeinterface`、`invokedynamic`；
- 控制转移：`ifeq`、`if_icmpge`、`goto`、`tableswitch`（也用于 `switch` 与异常表跳转）；
- 同步与异常：`monitorenter` / `monitorexit`（`synchronized`）、`athrow`（`throw`）。

<aside>
💡

字符串拼接、泛型、增强 for、try-with-resources、`switch(String)` 等都是**语法糖**：泛型在字节码中被擦除，try-with-resources 会被展开成嵌套的 `try-finally`，`switch(String)` 会转成 `hashCode` + `equals` 判断。

</aside>

## 执行引擎：解释器与 JIT 如何配合

### 先看一条完整路径

`.java` 源码先由 `javac` 编译成 `.class`（真实项目里通常由 Maven / Gradle 调用编译器完成）。运行时 JVM 加载 `.class`，读取其中的字节码。最开始由**解释器**逐条读取字节码并执行，这条路径启动快，是冷启动阶段的主要执行方式。随着同一段代码被反复执行，JVM 通过 **profiling**（运行时收集调用次数、循环次数、分支走向、实际类型等数据）识别出热点代码，触发 **JIT 编译**，把热点方法或循环体编译成本地机器码并缓存到 **Code Cache**，后续调用直接执行机器码。解释器与 JIT 默认并存：冷代码走解释，热代码走编译，优化假设失效时还能退回解释器。

**profiling 是什么意思？**

profiling 即“运行时性能剖析 / 行为画像”。在 JIT 语境下，它特指 JVM 在解释执行期间顺手收集的运行数据：方法调用次数、循环回边次数、分支走向、接口/虚调用的实际实现类、长期不变的值等。JIT 拿到这些数据才能做针对性优化，例如：某个分支 99% 走 true 时把另一分支变成冷路径、接口调用只出现一个实现类时做去虚化、对象未逃逸时做标量替换。这里的 profiling 是 JVM 自动、轻量、持续做的，和手动用 JFR / async-profiler 做性能分析同源，但目的是喂给 JIT 做优化。

### 先从最简单说起

假设 JVM 只做一件事：**读一条字节码，翻译成机器指令，执行一条**。这就是**解释器（Interpreter）**。

- 优点：启动快，拿到字节码立刻能跑，不需要先编译。
- 缺点：同一段代码每次都要重新“翻译”一遍。如果某个方法被调用一万次，或者循环执行一万轮，重复解释的开销就很大。

那能不能提前把方法整体编译成机器码？可以，这就是 **JIT（Just-In-Time）编译器**。

- 优点：编译后直接执行机器码，峰值性能高。
- 缺点：编译本身要花时间和 CPU。如果方法只执行一次，编译成本可能比解释执行还高。

所以答案是：**两者同时存在**。现代 HotSpot 默认运行在混合模式（mixed mode），冷代码用解释器，热点代码交给 JIT 编译后执行。

### 一段代码实际怎么跑

1. **第一次调用**：解释器逐条执行字节码；同时 JVM 在旁边做 profiling，记录方法调用次数、循环回边次数、分支走向等。
2. **判定为热点**：调用次数或回边次数超过阈值后，JVM 认为这是热点代码，触发 JIT 编译。编译通常在**后台线程**进行，不阻塞应用。
3. **编译完成**：该方法的后续调用直接执行机器码版本。对于正在执行中的长循环，可通过 **OSR（On-Stack Replacement，栈上替换）** 在循环中途切换到编译版本。
4. **编译结果缓存**：机器码存放在 Code Cache 中，供后续调用复用。如果运行时假设失效（例如后续加载了新子类导致多态变化），会发生**去优化（deoptimization）**，退回解释器继续执行，保证语义正确。

### 什么时候用解释器，什么时候用编译器

| 场景 | 使用 | 原因 |
| --- | --- | --- |
| 启动阶段、只执行一次的方法 | 解释器 | 无需等待编译，启动更快 |
| 反复调用的方法、长循环 | JIT 编译后的机器码 | 编译成本被多次执行摊薄，峰值性能高 |
| JIT 正在后台编译时 | 解释器继续执行 | 不阻塞应用线程 |
| 优化假设失效后 | 退回解释器（去优化） | 先保证语义正确，再重新收集信息 |

一句话总结：**解释器负责“马上能跑”和兜底，JIT 负责“跑得快”**，二者互补而不是二选一。

### HotSpot 的两个编译器与分层编译

- **C1（Client Compiler）**：编译快、优化少，适合快速预热；
- **C2（Server Compiler）**：编译慢、做激进优化，适合长时间运行的服务；
- **分层编译（Tiered Compilation）** 把执行级别分成 0~4：

| 级别 | 状态 |
| --- | --- |
| 0 | 解释执行，开始收集 profiling |
| 1 | C1 简单编译，不收集 profiling |
| 2 | C1 编译，带有限的 profiling |
| 3 | C1 编译，带完整 profiling |
| 4 | C2 编译，使用 profiling 做激进优化 |

热点探测依赖**方法调用计数器**和**回边（循环）计数器**；达到阈值就从低级别往高级别升级。

常用参数：

- 默认：混合模式（解释 + JIT + 分层编译）；
- `-Xint`：纯解释模式，禁用 JIT，便于对比排查；
- `-Xcomp`：尽可能在首次调用时编译（多用于测试，生产慎用）；
- `-XX:+PrintCompilation`：观察编译事件；
- `-XX:CompileThreshold`：传统阈值参数（不同 JDK 版本与分层编译下的行为会有差异，以实际版本为准）。

### 分层编译是 JVM 自动升级的吗

是。升级动作由 JVM 根据计数器和 profiling **自动完成**（0 → 1/2/3 → 4），不是靠参数逐级指定。参数只决定“开关和门槛”：

- `-XX:+TieredCompilation`（默认开）/ `-XX:-TieredCompilation`（关闭分层）；
- `-XX:TieredStopAtLevel=1`：只升到 C1，适合短生命周期应用，减少预热成本；
- `-XX:CompileThreshold` 以及各层级的 `TierX...Threshold` 类参数：调整升级阈值（不同 JDK 版本名称和可用性有差异）；
- `-Xint` / `-Xcomp`：极端模式，生产环境一般不用。

一句话：**参数决定“允不允许升级、门槛多高”，JVM 决定“什么时候升到哪一级”。**

### 为什么不提前彻底编译成机器码

先澄清阶段：`javac` 只产出 `.class` 字节码。彻底编译成机器码属于 AOT（如 GraalVM `native-image`）或 JVM 启动时的全量 JIT（`-Xcomp`），不是 `javac` 阶段的事。

- **运行时信息只有运行时才有**：分支概率、接口调用的实际实现类、哪些代码真正热。提前编译拿不到这些数据，优化决策只能靠猜。
- **只优化热点更划算**：典型服务里长期运行的热代码只占一小部分。全量彻底编译会把冷代码也编译掉，浪费启动时间和 Code Cache；分层 JIT 则让解释器先保证启动，再由 C1 快速预热、C2 深度优化热点。
- **Java 的动态特性需要兜底**：反射、动态代理、运行时类加载、字节码增强（Spring / MyBatis / Hibernate）都依赖运行时环境；优化假设失效时 JIT 还能去优化退回解释器。
- **启动时间与稳态性能的平衡**：全量彻底编译启动慢、预热长；分层 JIT 牺牲一点预热时间，换来基于运行时画像的高吞吐。服务端长进程能摊薄预热成本，因此 JIT 更划算；短任务、Serverless、CLI 才更倾向 AOT。

代价小结：AOT 启动快，但峰值吞吐通常低于充分预热的 JIT，且对反射/动态特性不友好；分层 JIT 用启动和预热时间，换更精准的优化与可回退性。

## 逃逸分析与相关优化

下面这些优化都属于 **JIT 在编译时**基于 profiling 做的工作，解释器不做这些优化。

**逃逸分析（Escape Analysis）** 判断一个对象是否只在当前方法/线程内使用：

- **不逃逸**：对象只在方法内部使用，未被外部方法或线程引用；
- **方法逃逸**：作为返回值或参数传给其他方法；
- **线程逃逸**：被其他线程访问（如写入共享静态字段）。

基于分析结果（`-XX:+DoEscapeAnalysis`，现代 JDK 默认开启），JIT 可做三项优化：

| 优化 | 含义 | 效果 |
| --- | --- | --- |
| **标量替换** | 把未逃逸对象拆成若干局部标量，字段用局部变量表示 | 不再真正创建堆对象，是 HotSpot “栈上分配”的主要实现方式 |
| **栈上分配** | 对象随栈帧创建/销毁 | 避免 GC 回收与堆分配开销；在 HotSpot 中通常由标量替换达成 |
| **同步消除** | 锁对象不会逃逸出线程，其他线程无法竞争 | 去掉 `synchronized`，减少锁开销 |

示例：

```java
public String build() {
    StringBuilder sb = new StringBuilder(); // 未逃逸：仅在本方法内使用
    sb.append("hello").append("world");
    return sb.toString();                   // 返回的是 String，sb 本身没有逃逸
}
```

<aside>
💡

逃逸分析是 JIT 的运行时优化，不是语言规范保证；对象是否真的被标量替换，需通过 `-XX:+PrintEscapeAnalysis`（诊断参数，可能需配合 `-XX:+UnlockDiagnosticVMOptions`）或 JFR 等工具观察，不应把“局部变量一定在栈上”当作编码前提。

</aside>
